# eSemnBun for Windows (F-13)

**eSemnBun** (codename *MoldSign* in code) is the native Windows app and CLI for qualified electronic signatures with
the Moldovan eID card (IDEMIA CosmoX ID-A, IAS/ECC) on a PC/SC reader (bit4id miniLector POCKET EVO). The C# core is
a line-by-line port of the Swift reference (`swift/MoldSignKit`), gated by the shared golden vectors in `../spec/vectors`.
Contracts: [`docs/09-architecture.md`](../docs/09-architecture.md), [`docs/10-design-system.md`](../docs/10-design-system.md)
(§0 v2 + §0.2b v3), [`spec/cli.md`](../spec/cli.md), plan items `WIN-*`, `UX-*` and `CLI-*` in [`PLAN.md`](../PLAN.md).

Naming (docs/10 §0.2b, UX-12): users see **eSemnBun** (window titles, tray tooltip, About, Start menu, installers, file
names), the app is `eSemnBun.exe` and the CLI command is `esemnbun`. The codename stays in code: projects and namespaces
`MoldSign.*`, the MSIX identity, `%LOCALAPPDATA%\MoldSign`, the Credential Locker resource, registry IDs, `MSIGN_PIN`.
Vendor references stay "MoldSign" (the STISC Java suite, the bridge protocol). Version: **0.2.0** (one source:
`Directory.Build.props`).

## The app (design v2/v3, UX-01, UX-02, UX-06, UX-09…UX-11)

* **Card = selector** (`Controls/CardWallet` + `IdCardFace`). The selected card is drawn as a stylized Moldovan ID
  card: pastel paper, guilloche waves and a rosette (Path geometry built in code, hue rotated ±20° per card from the
  certificate SHA-1), "REPUBLICA MOLDOVA / REPUBLIC OF MOLDOVA" and "CARTE DE IDENTITATE / IDENTITY CARD", a neutral shield
  outline (never the coat of arms), the gold chip, a grey portrait frame with a silhouette, Numele/Surname,
  Prenumele/Given name(s), Valabil până la/Valid until (`dd MM yyyy`, certificate notAfter) and Emitent/Issuer, and a
  status strip. Only certificate data: no photo, no document number, no IDNP. Fixed colors in both themes.
  With several cards, a horizontal carousel keeps the selected card centered with adjacent peeks, a position counter,
  previous/next buttons, touch scrolling and left/right keys. Selection identifies the reader for the next signature.
  Each card is an accessible button named with its holder, expiry and position. The component keeps a fixed height;
  no cards produce the dashed empty-state face. The tray does not expand into a vertical card list.
* **Several cards** (docs/09 §3.1b). `ReaderWatcher` reads PC/SC (`SCardGetStatusChange`, zero timeout, no connect) on
  every DeviceWatcher / CardAdded / CardRemoved event and every 2 s. `ReaderGenerationTracker` gives each insertion a
  generation (presence + the event counter in `dwEventState`), and `CardWallet` (Core, unit-tested) keeps per-card PIN-less
  reads, drops late answers for re-inserted cards, and keeps the selection. Signing goes to the selected card's reader
  with its certificate SHA-1 as the **identity guard**: read certificate → compare → SELECT ADF → VERIFY, so a swapped
  card fails with `CardChanged` before any PIN is sent; the app then re-reads the cards.
* **Tray** (UX-11): green dot when at least one card is inserted (reading, ready, signing), gray otherwise; tooltip
  "eSemnBun · Card conectat · {holder}" / "eSemnBun · Niciun card conectat" / the error one-liner. Glyph variants for
  dark and light taskbars (`SystemUsesLightTheme`). The five-state light (green/amber/blue/red/none, docs/10 §0.1) is in
  the flyout and window headers (`StatusLightPill`), and errors also show in the main window `InfoBar`.
  The Windows 10 crash immediately after the green dot appeared was traced on hardware to WinUI's
  `GeometryGroup` stroke-mask renderer (`UnwrapD2DGeometry` access violation). The card rosette now uses
  separate rotated paths rather than transformed ellipse geometries in a group; the patched installed
  app remains responsive on Windows 10 Pro 19045.
  Card removal also exposed an icon-ownership bug: H.NotifyIcon disposes the previous icon, so it must receive
  a clone rather than the cached original. The cache now owns its originals; ready/empty and theme changes
  hand off independent copies. Two physical insert/remove cycles were confirmed stable by the owner.
* **Sign page**: a large dashed drop zone with "Alege fișiere…"; once files are added, their list (with a format picker
  per document) and the drop zone, compact, under it. PDFs: PAdES-T (default), XAdES-BES, XAdES-T or XAdES-C (detached
  XAdES over the PDF bytes → `<name>-semnat.xml`); other files: the XAdES levels. The choice reaches
  `SigningService.Sign` (routing and real RSA signing covered by simulator tests).
* **Recents and Activity**: the log is kept in `%LOCALAPPDATA%\MoldSign\activity.json` (no PIN or certificate data).
  Document rows are shown only while the file exists (pruned at startup, when the flyout opens and when the Activity
  page is shown). The flyout's "Recente" lists existing documents only (browser requests stay on the Activity page),
  click = reveal in Explorer, "Golește lista" clears it at once; the Activity page clears the whole log after a
  confirmation dialog.
* **Verify**: one card per signature, with signer, local signing time, timestamp, level, integrity/RSA/trust-chain
  checks, timestamp-imprint status and expandable selectable technical details. Offline limitations explicitly
  identify the TSA-signature and revocation checks that were not performed. Mixed unconfirmed/valid results remain
  unconfirmed, invalid signatures take precedence, and unsigned files have their own neutral verdict. Detached
  XAdES documents can be added through an inline picker and are re-verified; choosing a replacement with the same
  basename replaces the old selection. Tray verification opens this same detailed page.
* **Fluent 2**: NavigationView + Mica, acrylic tray flyout, InfoBar for status and errors, system caption buttons
  (Snap layouts keep working). The primary Sign button uses the accent style only while it is enabled (default style
  while disabled). Every flyout action that opens something (pickers, settings, the window, Explorer) hides the flyout
  first; a sign/verify result reopens it. The main window is a normal app window (taskbar, Alt+Tab).
* **Start at sign-in** (Settings): StartupTask under MSIX; the HKCU Run key unpackaged; an HKLM value written by the MSI
  shows as "set by your administrator".

### Signing (environment variables only)

Nothing in the repository holds a certificate, key or password; the script reads only these variables:

| Variable | Use |
|---|---|
| `MOLDSIGN_SIGN_THUMBPRINT` | SHA-1 thumbprint of a code-signing certificate in `Cert:\CurrentUser\My` or `LocalMachine\My` |
| `MOLDSIGN_TIMESTAMP_URL` | RFC 3161 server for that mode (default `http://timestamp.digicert.com`) |
| `MOLDSIGN_TS_ENDPOINT`, `MOLDSIGN_TS_ACCOUNT`, `MOLDSIGN_TS_PROFILE`, `MOLDSIGN_TS_DLIB` | Azure Trusted Signing (used instead of the thumbprint); authentication through `AZURE_TENANT_ID` / `AZURE_CLIENT_ID` / `AZURE_CLIENT_SECRET`. CI fetches the dlib (`Microsoft.Trusted.Signing.Client`) when the endpoint secret is set |
| `MOLDSIGN_MSIX_PUBLISHER` | MSIX `Identity/@Publisher`, must equal the signing certificate's Subject (defaults to the thumbprint certificate's Subject) |
| `MOLDSIGN_MSIX_IDENTITY`, `MOLDSIGN_MSIX_PUBLISHER_DISPLAY_NAME` | MSIX identity name (Store: from Partner Center) and the publisher's display name |

The MSI registers **Sign with eSemnBun** in Explorer's classic context menu for files. On Windows 11,
choose **Show more options** to see it. The selected document is added to the signing screen of the
running app (or opens the app); signing still requires the normal user action and card authorization.
This registration is not yet available in the MSIX installer.

If the browser bridge ports are occupied, Settings offers **Identify app and reconnect**. It shows
the executable paths and process IDs owning those ports and asks the user to confirm before closing
them. Windows may deny access to a process; in that case close the identified app manually and retry.

The script signs `eSemnBun.exe`, `eSemnBun.dll`, `MoldSign.Core.dll` and `esemnbun.exe` before they go into the MSI,
then the `.msi` and the `.msix`. Without any variable the artifacts are unsigned: the MSI still installs (SmartScreen
warns), but an unsigned MSIX does not install (use `-SelfSignForTesting` and trust the exported `.cer` on the test machine).

## CLI (spec/cli.md)

The command is `esemnbun`. `readers`, `cert [--out f.der]`, `sign-hex <digestinfo_hex>` are real. `sign`, `xades`,
`verify`, `server`, `cms-for-hash` print `error: not implemented yet (WIN-01)` and exit 1. Global options:
`--reader <name|substring>` (default: first reader with a card), `--quiet`, `--pin-stdin`. PIN order: `--pin-stdin` →
`MSIGN_PIN` → prompt without echo (`Console.ReadKey(intercept: true)`); `--pin` is rejected. Exit codes: 0 ok,
1 usage/unexpected, 2 verify invalid, 3 wrong PIN (remaining attempts on stderr), 4 PIN blocked, 5 no reader/card
(and non-Windows), 6 network.

```powershell
dotnet publish src/MoldSign.Cli -c Release -r win-x64 -p:PublishAot=true     # must run ON Windows
dotnet publish src/MoldSign.Cli -c Release -r win-x64 --self-contained -p:PublishSingleFile=true   # from macOS/Linux
```

## Deliberate deviations from the Swift reference (APDU bytes unchanged)

* **CMAC of the empty message** follows RFC 4493. `cpcsc.c` writes the pad byte out of bounds there; the card
  protocol never MACs an empty message, and the vectors include NIST's empty case.
* **READ BINARY unpads once.** `Card.swift` ISO-unpads each chunk again after `SecureChannel.unwrap` already did,
  which truncates any 128-byte chunk ending in `00`/`80`. It never fired on the reference card (no chunk boundary of
  its 1799-byte certificate ends in those bytes); a test covers it here. Swift should get the same fix.
* Malformed plain APDUs (Lc beyond the body, extended length) throw instead of being silently mangled.
* Like Swift, SM responses without tag 8E are accepted; rejecting them is TODO(WIN-01) once Swift changes first.
* Card-face name fallback (no SN/GN in the certificate): the common name is split at the first space as
  "{given name} {surname}" (X.509 CN order, "ION POPESCU" → surname POPESCU).

When testing resumes:

2. On Sign, choose a PDF, then drag another file onto the drop zone. The app now uses the Windows App SDK

4. Enable browser connection and try msign.gov.md from Chrome/Edge on that PC: available identity,

   stays running. The private HTTPS identity has been installed; it is not part of public source/artifacts.
5. If startup fails, collect Application Error/.NET Runtime events and `%LOCALAPPDATA%\MoldSign\errors.log`
   (exception type/HRESULT/call sites only, no PIN or document payload). The pre-port installed files are

HTTPS identity: the MSI and MSIX ship `localhost.p12` next to `eSemnBun.exe` (D-03), so a fresh PC needs no setup.
Settings → **Import HTTPS identity (localhost.p12)…** replaces it (e.g. after a vendor renewal) by copying to
`%LOCALAPPDATA%\MoldSign\localhost.p12`, which wins over the bundled copy; `MSIGN_TLS_P12` overrides both. Import
validates the hostname/private key/expiry and restarts an enabled bridge. On Windows, the loader uses
`UserKeySet` (without `PersistKeySet`); Schannel cannot serve the ephemeral PKCS#12 key used on other OSes.
Web-page PIN fields are ignored; the user approves in the app. Batch PIN reuse is memory-only, same origin
and certificate, five-minute expiry; unanswered browser PIN sheets expire after two minutes.

Known signing/validation limits: encrypted PDFs, compressed catalog/AcroForm dictionaries and indirect
Fields arrays are unsupported. The validator checks timestamp imprints but does not authenticate the TSA
signature or revocation status; chain checks use current time. CLI commands still have their separate
unfinished adapters listed above. The new Windows app build is installed locally, **not yet published to
the GitHub release**. The postponed test reminder was cancelled after testing resumed.

## Card carousel, preferences and reproducible UI scenarios

The card selector is a horizontal carousel with touch scrolling, left/right keys, previous/next buttons and a
compact position dots. The selected card is centered on a full-width page; adjacent cards do not appear as clipped slivers. Hover arrows sit in the side gutters. The card face uses the golden ratio, the portrait frame is 3:5 with an unstretched circular-head silhouette, and the contact chip sits
at the centre of the right margin. The neutral shield has explicit geometry bounds to prevent WinUI from
stretching its outline.

Settings offer a persisted Romanian/English/Russian language override (updates the open windows immediately), system/light/dark
appearance (applies immediately), saved-PIN permission and deletion, and **Open app when a card is inserted**.
The independent `eSemnBun.Watcher.exe` process can open a closed app on reader or card insertion. The two options are
independent. Unpackaged installations register a per-user Run entry; MSIX declares a separate, user-controlled helper
startup task. The helper remains alive when the UI quits and exits when both options are disabled. No privileged service
is installed, and the helper never connects to a card or accesses a PIN. Card presence includes muted cards so their errors
can be inspected. Starting the helper establishes a baseline rather than opening the UI for an already-present reader.

`AppServices` accepts `AppServiceDependencies` for reader discovery, transport, certificate reads, signing, verification,
credentials, authorization and browser lifecycle. `IDocumentSigner` and `IDocumentVerifier` are separate interfaces.
`DocumentBatchSigner` owns frozen batch sequencing and concurrency; `BrowserConnectionController` owns browser lifecycle.
`MoldSign.Desktop` owns atomic non-secret preferences, insertion policy and current-user activation IPC. `ReaderWatcher` is the production reader
source; `DemoReaderSource` publishes deterministic reader snapshots without opening PC/SC. In a Debug build, set `MSIGN_DEMO_CARDS`
to `none`, `empty`, `mute`, `reading`, `1`, `multiple`, `multiple-second`, `3`, `blocked`, `stuck`, or `signing`; optional `MSIGN_DEMO_DARK=1` and `MSIGN_DEMO_PAGE=sign|card|settings|verify|activity`
choose appearance and page. Demo certificates are fictional, signing and the browser bridge are disabled, and
settings/history remain untouched. `windows/scripts/capture-scenarios.ps1 -App <absolute-path-to-eSemnBun.exe>` captures
110 baseline window states in the current interactive desktop session to the Desktop screenshot folder. This matrix
covers baseline navigation and reader states; signing/consent/result scenarios still need a richer injected signing service.

Capture subsets with `-Scenarios @('multiple','multiple-second') -Pages @('card') -Themes @('light')` when checking
carousel changes. `MSIGN_UI_DIAGNOSTICS=1` enables a bounded, stage-only startup trace in the user's temporary folder
(`esemnbun-ui-startup.log`); it records no PINs, certificate values or document paths. Environment-driven mock mode
is ignored by Release builds. The language picker follows the system's first supported preference when set to System;
the application resolves that preference on every launch so a persisted MSIX override cannot leave an old language active.

Every capture waits for a unique app-generated readiness marker: the requested page must be loaded for three rendering
frames and any carousel must be centered on the selected card. The script validates the process/page/scenario and
foreground window before reading screen pixels, then stores the readiness JSON beside the PNG. Demo navigation disables
page transitions and ignores stale NavigationView selection events. These checks prevent a correctly named file from
silently containing the previous page or another window.

Local multi-document signing freezes the selected jobs, reader and certificate, then uses one short-lived
`BatchConsentSession`. The first approval lists every document and format; a remembered PIN uses one batch approval
followed by Windows Hello. The typed-PIN sheet lists the batch in a scrollable area. Later files reuse that batch's
PIN in memory, while each file still checks the card's certificate before VERIFY. Cancellation, a rejected PIN,
card replacement or any failure stops the batch without retries; the scoped session drops its PIN/provider references
at the end. PIN persistence remains an explicit Remember choice; managed string PIN APIs cannot guarantee memory zeroing.

`capture-scenarios.ps1 -App <Debug-executable> -PinOnly` captures the standalone batch PIN window in light and dark.
The Debug-only fixture lists three fictional files and a fictional holder, leaves the PIN empty, and exits on cancel
or after 30 seconds. It returns before constructing app services, so it cannot access signing, readers, saved PINs or
Windows Hello. The capture script validates the actual PIN-window handle/empty-field marker and closes it gracefully.


The Card carousel uses up to a 560px viewport with a 320px selected face and readable faded neighbor previews. Sign and
tray faces are capped at 280px, with a compact viewport up to 480px. Narrow tray windows page full cards without tiny
neighbor slivers. The Card page scrolls vertically, including wheel input over the horizontal carousel, and supports
Home, End, Page Up and Page Down. `scripts/test-card-page-scroll.ps1` checks real wheel and keyboard access to the final
saved-PIN action/help at 1100 × 720 and 900 × 580, with the second card fully visible and centered after resizing. PIN dialogs use a480px content column and a larger,
centered input. Portraits use the shared circular-head/short-shoulder geometry; chips contain exactly eight contact regions.

Ordinary launches show the main window, including later manual launches after setup. `--autostart` keeps subsequent
login launches in the tray. A current-user/session named-pipe broker forwards window activation and selected document paths; it never
accepts PINs or performs signing. Document launches pass only selected file paths into the signing queue. Package builds publish and include the independent helper in MSI/MSIX.

`test-insertion-helper.ps1` drives the Debug helper through an injected reader snapshot source and isolated preference file:
it waits for the helper's baseline-ready marker, inserts a synthetic reader, closes the resulting mock app, inserts a card,
and disables both options. `test-first-launch.ps1` runs the ordinary app without mock/force-show switches against a fresh
isolated Debug profile and verifies first and subsequent manual launches. It requires detached smart-card readers and
performs no signing actions. `MSIGN_TEST_PREFERENCES` only exists in Debug builds and isolates activity storage too.

## User demo mode

Settings offers a persistent demo switch in Debug **and Release**. Confirming entry stops the current
reader/browser services and opens a sample-only sandbox with fictional cards. A persistent disclaimer
marks every demo screen. Choosing documents loads bundled/generated samples; signing and verification
complete through mock services. Outputs are explicitly `DEMO-NOT-SIGNED` and contain no valid digital
signature. External documents are rejected and never read. Saved PIN storage and real history stay
untouched. Leaving demo restores normal services.

`windows/scripts/test-demo-mode.ps1` exercises this through native controls in an isolated test guest,
restoring its preferences/history afterward. It does not require a card or a Debug fixture environment.

## Explorer commands

Sign and Verify are available from Explorer. The MSI classic verbs use resources 101 and 102 in `eSemnBun.Explorer.dll`, with Romanian, English and Russian exported from
`localization/catalog.json`. The MSIX registers the native `IExplorerCommand` with a COM surrogate and
`windows.fileExplorerContextMenus`; they appear directly in the Windows 11 menu. Sign queues selected files and does not authorize a signature; Verify opens verification. Both forward to an existing application instance. The DLL architecture must match Explorer: use the ARM64 package on ARM64.

`package-windows.ps1` builds the shell DLL before publishing. `scripts/build-explorer-command.ps1` downloads a pinned,
SHA-256-verified portable llvm-mingw compiler into the user's local build cache and embeds the localized resource.
No compiler registration or system-wide installation is required. To build an MSIX directly, first build the DLL into
`src/MoldSign.App/ShellPayload` for the selected target architecture.

## Taskbar actions and signing results

The taskbar jump list offers Sign and Verify, plus up to eight existing signed documents. Store installations use the packaged jump-list API; standalone installations use the Windows Shell API and the MSI shortcut's `md.esemnbun.desktop` identity. Removed entries are respected, and Windows may hide recent documents when document history is disabled. Standalone history stores paths in `%LOCALAPPDATA%\MoldSign\taskbar.json`; demo outputs never enter the real taskbar history.

Completed outputs remain on the Sign page as links that reveal the file in Explorer. Partial success keeps completed outputs while leaving the failed input queued with its error and retry action. The page uses one vertical scroll area so documents and controls remain reachable in shorter windows.

### Temporary standalone MSI certificate

GitHub Actions can sign only the standalone MSI using `WINDOWS_MSI_CERTIFICATE_PFX_BASE64` and `WINDOWS_MSI_CERTIFICATE_PASSWORD`. The public `eSemnBun-self-signed.cer` is exported beside the installer. This does not change the Store MSIX publisher or signing. The certificate is self-signed and does not establish public Windows trust; recipients must explicitly trust it. Keep the private PFX/password only in GitHub Actions secrets and the owner's offline secrets folder.
