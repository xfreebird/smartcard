# Encryption-certificate investigation — 19 November 2026

The physical iPhone 13 Pro/card/bit4id reader now passes public-certificate export and independently generated encrypted-file decryption. The owner reported the initial failure on Android, requested the latest iOS app, and explicitly selected Card public key compatibility after the card's actual decipher capability was established.

## Cause and changes

- The secure-response decoder rejected non-success outer statuses before authenticating the protected body. Real directory reads return outer `6282` for a short final chunk and `6B00` past an exact block boundary. Swift and Kotlin now require the complete response MAC and matching authenticated status for any non-success outer status. Existing structure/MAC/padding checks remain mandatory.
- Directory reads obtained EF `7001` (347 bytes), `7002` (2048) and `7005` (4000). They list one RSA-4096 key with decipher/unwrap usage, associated with PIN ref03 using UTF-8 metadata, and one certificate with critical Non Repudiation usage only. Numeric input now supports ASCII-numeric and UTF-8 metadata; unsupported encodings/references stay unavailable.
- Public DOCP reads established a 512-byte, non-repudiation-flag-zero key whose decipher access condition requires user authentication. The PIN object is global under MF; the RSA key is under Generic ADF. No PIN was needed to obtain these descriptors.
- The vendor's CosmoX decipher implementation supplied the reviewed command sequence. The vendor Java file-encryption policy does not check keyEncipherment. Certificate purpose and actual card-key capability are distinct; the app does not silently reinterpret one as the other.
- Added explicit Card public key compatibility policy in Swift/Kotlin and Apple/Android forms, with EN/RO/RU text. Default certificate mode still requires keyEncipherment. Compatibility uses the certificate as a public RSA key container; decryption still checks CMS structure/recipient, unique card metadata, modulus size and exact re-discovered identity before VERIFY.
- Restored public DER export with no document/PIN requirement. The Apple form now retains a completed public read across transient CryptoTokenKit slot/generation/certificate-hydration changes, while rejecting changed reader/certificate selection. A disconnected reader cannot admit PIN-based decryption; the core freshly binds the actual identity before VERIFY.

## Physical evidence

- Target: physical iPhone 13 Pro / iOS 27.2, bit4id miniLector POCKET EVO, owner's inserted electronic ID. Source base `6666aa27` plus this working patch.
- Synthetic RSA primitive: one PIN verification and one decipher recovered the exact random 16-byte challenge. No signature was created.
- File acceptance: OpenSSL independently encrypted a synthetic 4096-byte original using the exact exported certificate, RSA PKCS#1 v1.5 transport and AES-128-CBC. The production card decryption method, called from the isolated probe with explicit compatibility policy, restored all 4096 bytes exactly. A separate local comparison after device retrieval passed. Original/restored SHA-256: `c8f5d0341d54d951a71b136e6e2afcb14d11ed8489a7ae126a8fee0df6ecf193`.
- The file check also produced a CMS envelope through the app's native encryption codec. The certificate used for it was byte-identical to the selected card certificate.
- Actual eSemnBun build 11 UI: Documents → Protect files → RSA certificate → enable compatibility → Read my card → Export public certificate. Saved through the native Files picker to On My iPhone → eSemnBun. Retrieved only the new `.cer`; all 1799 bytes match the tested certificate. No document or PIN was selected for this export. No upload or third-party sharing occurred.
- Inspected the UI through iPhone Mirroring. Both private experiments have distinct persistent locks created before VERIFY. Retrieved reports prove each sent exactly one VERIFY and one decipher, with no automatic retries. Both succeeded.

## Build, privacy and limits

- Installed eSemnBun 0.2.13 development build 11 and the separate Certificate Probe (`md.esemnbun.certificateprobe`) build 12. Existing app data was retained; no uninstall was performed. Main-app builds use Xcode 27.1 RC; the default Xcode 26.6 fails on an existing `appEntityIdentifier` API call. Probe development signing and its separate application identifier were inspected.
- The owner explicitly requested the supplied PIN embedded in temporary probe builds. Private plist inputs stayed in mode-0600 files under ignored `.local/`; no PIN was placed in tracked sources, build arguments or logs. After each private check a normal probe build replaced it. Final build 12 contains no embedded PIN; private input files were removed, source/log checks passed, and reports/attempt locks were retained. The shipping app never received a hardcoded PIN.
- Reports, public certificate bytes and synthetic outputs stay in ignored `.local/certificate-reader-2026-11-19/` and file-protected probe storage. The stable local certificate export is `.local/certificate-reader-2026-11-19/export/public-certificate.cer`. Do not commit these identity-bearing files or diagnostic payloads.
- Native iOS/probe builds, actual card reads, both controlled private checks, UI export, byte comparisons, whitespace and localization generation/drift checks passed. Added regression sources for mirrored EOF/MAC/status handling, block-boundary reads, UTF-8 numeric metadata, explicit compatibility and command admission. Automated suites were not run under the owner's standing rule.
- Android source/resources were updated but its build and physical runtime were not run. Shared macOS/iPad UI and other card generations remain unvalidated. The subsequent [platform parity change](card-public-key-platform-parity-2026-11-19.md) extends the explicit option to Windows, Linux UI and both CLIs; those native builds/runtime checks remain pending. The CMS wire format is unchanged.
- The file decryption used the production service through the probe. The main app's certificate read/export controls were driven end to end; its full file-picker/encrypt/decrypt/save journey was not separately repeated. No release, store submission, commit or push was requested or performed.
