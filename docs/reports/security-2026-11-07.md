# Security review — 2026-11-07

Scope: source review of Apple, Android, Windows and Linux PIN storage, bridge authorization, session lifetime and debug entry points. No real card, PIN, private credential or production signing operation was used. This is a focused review, not a penetration-test certification.

## Fixed

1. **Bridge result authorization (Swift and Android).** Result polls previously checked only a session identifier after the global origin allow-list. A different allowed origin that obtained an identifier could consume the signed document/result; Swift could also alter PIN retention before checking whether the session existed. Sessions now retain the creator origin and reject mismatching polls with 404 before mutation. Windows already checks `session.Origin`. Evidence: Swift `Bridge/Server.swift` `newSession`/`poll`, Android `SigningBridgeRoutes.kt` `Session`/`poll`, Windows `BridgeHost.cs` `PollAsync`. This requires a leaked identifier; identifiers are random and this review did not find a cross-origin identifier leak.

2. **Swift long-poll PIN cleanup race.** A normal poll arriving while consent/signing was still pending called `forgetPIN` before signing added the remembered PIN. The result callback now clears the PIN after completion unless `keep_pin_session=1`. The origin check precedes this action. The portal batch test now checks foreign-origin result rejection and requires fresh consent when reusing a completed non-retained session.

3. **Apple Release keychain downgrade.** `PinVault.save` could silently store a legacy item without the Keychain `.userPresence` ACL when the data-protection keychain entitlement was missing, or access-control creation failed. Only DEBUG builds now allow this fallback; Release saving fails closed. Release discovery and reads now also ignore legacy records. Users must enter their PIN manually and save again after successful signing; old records are not silently trusted. Existing legacy records remain stored until the same card is saved again or explicitly deleted; ignoring them is not erasure. DEBUG retains its development fallback.

4. **Swift browser filesystem access.** Path-based signing/verification routes now reject any supplied Origin or Sec-Fetch-Site, before payload parsing, consent or file access. This applies even to an allowlisted origin supplying the desktop header. Native header-based requests and explicitly enabled legacy desktop clients remain supported. Regression checks cover both browser origins and originless fetch metadata; the existing Java desktop compatibility test remains in the focused suite.

5. **Android ciphertext/card binding.** Saved-record AES-GCM now authenticates a versioned certificate identifier as associated data. Version-1 records are ignored, requiring manual PIN entry and successful signing before a new biometric-confirmed save; the legacy entry is removed on save/delete. Modified or moved version-2 records fail authentication and return the manual-entry path without submitting a PIN. An attacker needs access to private app storage to move records, and OS key ownership plus biometric approval remain prerequisites. A JVM test exercises actual AES-GCM encryption/decryption with matching and mismatched certificate bindings. Corrupt/short encoded records also fail closed.

6. **CLI detached XAdES reference containment.** CLI verification now reads referenced documents through `DetachedDocumentAccess` beneath the caller-selected document directory. It rejects traversal, absolute paths, malformed components and symlinks, opens each component relative to a held directory descriptor using `openat`/`O_NOFOLLOW`, and accepts only regular files. `O_NONBLOCK` prevents a FIFO reference from hanging verification before its type is checked. The selected root may intentionally resolve a user-selected alias. Independent source review found no material flaw for the hostile-document-reference threat; focused tests cover valid Unicode/nested files and rejected escape/symlink references. Final expanded Swift test results are recorded by the coordinating run.

## Verified controls in source

- Apple saves protected entries with `WhenUnlockedThisDeviceOnly` and `.userPresence`; reads explicitly evaluate device-owner authentication. No cloud-synchronizable flag is set.
- Android encrypts saved PINs using Android Keystore AES-256-GCM, authentication required per key use, strong-biometric `CryptoObject`, and invalidation on biometric enrollment. Plain byte buffers are wiped in `finally`; mutable bridge PIN arrays are cleared on removal. Manifest disables backup and keeps its bridge service unexported.
- Windows gates app PIN retrieval on successful `UserConsentVerifier`, and stores credentials with `PasswordVault`. It rejects non-loopback bridge requests and binds results/PIN sessions to origin. Browser callers cannot invoke filesystem signing routes.
- Linux stores PINs through libsecret and explicitly documents that the session-unlocked Secret Service has no per-read user-presence gate. Its nonpageable libsecret buffer is freed securely; the returned Swift String is a separate copy.
- Bridge policies require matching allowed origins; the desktop compatibility header does not override a supplied disallowed origin. Swift listeners explicitly bind loopback. Preview/demo certificate mode rejects signing. Reviewed Apple and Windows demo entry points are DEBUG guarded.
- Saved PIN and reusable batch sessions carry certificate identifiers; card signing paths check the selected certificate before PIN verification. Random session identifiers and explicit consent remain relevant defenses in addition to origin checks.

## Residual issues and limitations


- **OS presence differs by platform:** Windows Hello is an application check before Credential Locker retrieval, not a cryptographic per-use restriction on the stored secret. Linux uses session-unlocked storage and application consent. Neither should be described as equivalent to Android auth-bound encryption or Apple protected Keychain ACLs. Same-user malware and a compromised process remain outside those application gates.
- **PIN lifetime:** Swift and C# Strings cannot provide deterministic zeroization. Five-minute batch expiry is enforced when sessions are consulted/swept; it is not proof that plaintext has been physically erased from process memory exactly at five minutes. Stopped servers clear maps, but no heap inspection was performed.
- **Native bridge identity:** the compatibility header is public protocol text, not a secret or native-client authentication. Local processes can forge origins/headers. Consent and card identity checks are essential. The broad vendor domain wildcard policy includes HTTP sites and should not be treated as authenticated trust in an individual application.

- No live biometric cancellation/enrollment, Keychain entitlement failure, Windows Hello, Linux locked-keyring, rooted-device, malicious local-process, or signed Release artifact tests were performed in this review. Existing Apple legacy records were not enumerated or retrieved. No actual secrets were searched or printed.
