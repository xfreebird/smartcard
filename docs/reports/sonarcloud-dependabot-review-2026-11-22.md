GitHub labels the npm entries “runtime” because the Docusaurus toolchain is in `dependencies`; the deployed website is static files, and these particular Node packages run during build/development. Tooling vulnerabilities still matter because developer machines and CI may have access to sensitive artifacts. Source/dependency-controlled build inputs are the relevant trust boundary here; no public visitor-to-build execution path was found. Absence of an alert is not proof that all Gradle/NuGet/Swift/system dependencies are covered or safe.

## Recommended implementation order

1. Fix workflow input handling and the CMAC error path in separate, focused changes. Add failure-path verification before any signing release.
2. Take the narrow Addressable patch after complete CI succeeds; bound Windows document/origin regex execution.
3. Update the website's vulnerable build dependencies with compatibility validation. Keep the UUID finding scoped to its unaffected v4 consumer until a parent update is suitable.
4. Pin external actions, narrow publishing permissions, then address SafeHandle lifetime and cancellation/shutdown ownership.
5. Configure Sonar test roots, coverage and a new-code gate; record narrowly justified compatibility/false-positive decisions. Re-scan before choosing a remaining cleanup target.

Do not schedule a broad crypto rewrite, blanket HTTP-to-HTTPS replacement, shell-style migration or coverage-score chase from this initial scan. The encryption integrity limitation is real but already explicit in the interoperability contract; changing that format deserves its own design and compatibility decision.
